# PetApp 项目 AI 开发指导书

## 一、开发过程中出现的问题与原因分析

### 1.1 编译错误类问题

#### 问题 1：文件编码导致编译失败（C4828 警告 + 语法错误）
**现象**：MSVC 报 C4828 警告，提示文件包含当前代码页（GBK）无法解析的字符，随后大量语法错误。
**原因**：
- AI 生成的 C++ 源文件包含中文注释或中文字符串
- 文件保存为 UTF-8 编码，但 MSVC 默认使用系统代码页（Windows 中文系统为 GBK）解析源文件
- 虽然 CMake 添加了 `/utf-8` 编译标志，但某些情况下 MSVC 仍无法正确处理 UTF-8 BOM 或无 BOM 的 UTF-8 文件
- 特别是当文件中同时包含 ASCII 和中文字符时，MSVC 的 UTF-8 解析可能失败

**具体案例**：
- `skill_ocr/main.cpp`：中文注释导致编译失败
- `skill_translate/main.cpp`：中文字符串（如 `"你好"`）导致编译失败
- `MainWindow.cpp`：中文注释导致编译失败

**解决方案**：
- 移除所有中文注释，改为纯英文注释
- 中文字符串使用 `u8"..."` 前缀（C++17）或 `\x` UTF-8 字节转义序列
- 使用 Python 脚本生成包含中文的 C++ 文件，确保正确的 UTF-8 编码

#### 问题 2：Qt API 弃用警告（C4996）
**现象**：`QMouseEvent::globalPos()` 被弃用，产生 C4996 警告。
**原因**：
- Qt 6.x 弃用了 `globalPos()`，推荐使用 `globalPosition().toPoint()`
- AI 在生成代码时使用了旧版 API

**解决方案**：
- 将 `event->globalPos()` 替换为 `event->globalPosition().toPoint()`

#### 问题 3：CMake 找不到 Qt 组件
**现象**：`find_package(Qt6 REQUIRED COMPONENTS TextToSpeech)` 失败。
**原因**：
- 当前 Qt 6.8.3 安装未包含 TextToSpeech 模块
- AI 默认假设所有 Qt 组件都已安装

**解决方案**：
- 将 TextToSpeech 从 `REQUIRED` 改为 `QUIET` 可选查找
- 使用条件编译 `#ifdef HAS_TEXT_TO_SPEECH` 处理无 TTS 的情况

#### 问题 4：命名空间冲突
**现象**：在 `namespace petapp::core` 内部使用 `class QFileSystemWatcher*` 前置声明时，编译器将其解析为 `petapp::core::QFileSystemWatcher`。
**原因**：
- AI 在命名空间内部使用前置声明，编译器将其解析为当前命名空间下的类型
- 这是 C++ 命名空间解析的常见陷阱

**解决方案**：
- 改为直接 `#include` 头文件，而不是使用前置声明

#### 问题 5：参数名与基类成员冲突（C4458 警告）
**现象**：lambda 参数名 `data` 隐藏了 `QWidget::data` 成员。
**原因**：
- AI 使用了 `data` 作为参数名，但 `QWidget` 基类已有 `data` 属性
- 这是 Qt 框架中常见的命名冲突

**解决方案**：
- 将参数名从 `data` 改为 `variant`

### 1.2 运行时问题

#### 问题 6：鼠标拖动逻辑错误
**现象**：鼠标只能在窗口特定区域按下才能拖动，而不是任意位置。
**原因**：
- AI 生成的 `mousePressEvent` 中，`if (event->button() == Qt::LeftButton)` 条件正确
- 但 `mouseMoveEvent` 中缺少 `if (event->buttons() & Qt::LeftButton)` 检查
- 使用了弃用的 `event->globalPos()` API

**解决方案**：
- 在 `mousePressEvent` 中设置 `m_dragging = true` 并记录起始位置
- 在 `mouseMoveEvent` 中检查 `event->buttons() & Qt::LeftButton`
- 使用 `event->globalPosition().toPoint()` 替代 `event->globalPos()`

### 1.3 文档问题

#### 问题 7：文档不一致
**现象**：各文档之间存在版本号、路径、功能描述的不一致。
**原因**：
- AI 在生成多个文档时，没有保持统一的上下文
- 文档生成时间不同，部分信息已过时
- AI 对项目实际代码的认知不完整

**具体案例**：
- 版本号不一致（工作报告 vs 操作手册）
- 文件路径不一致（`data/models/tesseract.exe` vs `data/models/`）
- 功能描述遗漏（VoiceManager 情感调节功能未实现但文档提及）

### 2.3 语言要求

#### 2.3.1 源文件编码
```
- 所有 .cpp 和 .h 文件必须使用 UTF-8 编码（无 BOM）
- 禁止在源文件中包含任何非 ASCII 字符（中文注释、中文字符串等）
- 中文字符串必须使用以下方式之一：
  a) u8"你好" 前缀（C++17 标准）
  b) \x 转义序列：\xe4\xbd\xa0\xe5\xa5\xbd
  c) 从外部 JSON 文件加载
- 注释必须全部使用英文
```

#### 2.3.2 代码规范
```
- 使用 C++17 标准
- 遵循 Qt 编码风格（类名大驼峰、函数小驼峰、成员变量 m_ 前缀）
- 头文件使用前置声明代替 #include（但注意命名空间问题）
- 禁止在头文件中包含 windows.h
- PlatformDefines.h 作为每个 .cpp 的第一行
- 使用 Q_UNUSED() 宏处理未使用参数
```

### 2.4 架构逻辑要求

#### 2.4.1 模块分层
```
必须严格遵守三层架构：
1. 核心层（Core）：EventBus、MemoryModule、HeartbeatModule、EmotionModule、CapabilityManager、SkillManager
2. 表现层（Appearance/UI/Voice/Action）：AppearanceManager、VoiceManager、ActionManager、MainWindow 等
3. 技能层（Skills）：skill_echo、skill_translate、skill_ocr、skill_chat

规则：
- 层间只能通过 EventBus 事件通信
- 禁止跨模块直接函数调用
- 核心层不能依赖表现层
- 技能层是独立进程，通过 JSON/stdin/stdout 通信
```

#### 2.4.2 事件总线通信
```
所有模块间通信必须通过 EventBus：
- 发布：EventBus::instance().emitEvent("event_name", data)
- 订阅：EventBus::instance().on("event_name", callback)
- 取消：EventBus::instance().off("event_name", callback)

预定义事件列表（必须使用这些事件名）：
- heartbeat：心跳触发
- emotion_changed：情感变化
- online_status_changed：网络状态变化
- show_bubble：显示气泡
- settings_changed：设置变更
- voice_command：语音指令
- action_command：动作指令
```

#### 2.4.3 技能插件协议
```
技能插件为独立控制台 exe，必须遵循 JSON 行协议：

请求格式（宿主 → 技能）：
{"method":"execute","id":1,"params":{"input":"...","config":{...}}}

响应格式（技能 → 宿主，成功）：
{"id":1,"result":"处理结果","error":null}

响应格式（技能 → 宿主，失败）：
{"id":1,"result":null,"error":{"code":-1,"message":"错误信息"}}

规则：
- 单次任务后退出，禁止长连接
- 5 秒超时保护
- 支持任何语言编写的 exe
```

#### 2.4.4 离线优先
```
- 默认关闭网络
- 所有技能必须有本地实现
- 技能 manifest.json 中 requires_network 字段控制网络需求
- 网络不可用时，依赖网络的技能自动禁用
- 自适应降级流程：
  用户点击技能 → CapabilityManager.isNetworkAvailable()
  → SkillManager.canRunSkill() → 执行或提示
```

## 三、总结

### 3.1 核心教训

1. **编码问题是最大障碍**：MSVC 对 UTF-8 的支持不完善，必须严格避免源文件中的非 ASCII 字符
2. **Qt 版本差异**：Qt 6.x 弃用了许多 Qt 5.x 的 API，AI 需要明确知道当前使用的 Qt 版本
3. **组件可用性**：AI 不能假设所有 Qt 组件都已安装，必须使用 QUIET 模式
4. **命名空间陷阱**：C++ 命名空间解析规则复杂，AI 生成代码时容易出错
5. **文档一致性**：AI 生成多个文档时容易产生不一致，需要交叉验证

### 3.2 最佳实践

1. **分步验证**：每次修改后立即编译验证，不要累积修改
2. **使用脚本生成**：对于包含非 ASCII 字符的文件，使用 Python 脚本生成
3. **明确告知环境**：在每次对话开始时，明确告知 AI 当前的工具链版本和路径
4. **指定 AI 角色**：明确告知 AI 它应该扮演的角色和专业领域
5. **提供错误日志**：编译失败时，提供完整的错误日志给 AI 分析
